# 05: 动作按钮 + 答案区 Markdown 渲染

**What to build:** **结果窗口**分成上下两区：上半区是识别出的可编辑**文本**，下半区显示**动作**的答案并渲染 Markdown。三个动作按钮：翻译成中文、总结、表格转换。点一下，答案在下半区流式逐字出现。动作以「当前编辑后的文本」为输入。

**Blocked by:** 03

**Status:** ready-for-agent

- [x] 结果窗口下半区为渲染 Markdown 的答案区（粗体、列表、代码块、表格）
- [x] 「翻译成中文」按钮：把当前文本翻成中文，答案流式显示在下半区
- [x] 「总结」按钮：给出当前文本的几句话概括
- [x] 「表格转换」按钮：把文本中的表格转成 Markdown 表格
- [x] 上半区始终是纯文本编辑框，不被 Markdown 渲染影响
- [x] 每次动作都取「当前编辑后的文本」，而非最初的识别结果
- [x] 同一次识别可连续做多个动作，答案随之更新
- [x] `PromptBuilder` 有自动化测试：三个动作各自产出预期指令

**Comments**

真机端到端验证（真实 opencode-go 端点）：识别「Hello world」→ 翻译得到「你好，世界」→ 把编辑器改成一张表 → 表格转换得到规范 Markdown 管道表格（`| 姓名 | 年龄 | 城市 |` + `| --- |`），且渲染后 `toPlainText()` 不再含 `|`（证明真的渲染成了表格）→ 总结得到中文概括。编辑器全程保持纯文本。

一次识别偶发返回空（疑为限流），重跑即正常。

代码审查（Standards / Spec 两轴）后修复：

- `start_recognition` 里 `_editor.clear()` 在 `_filling_text = True` **之前**触发 `textChanged`，把控制器文本提前清空——调整顺序。
- 无并发守卫，两个流可能同时写入同一控件——加 `is_busy()` 前置判断。
- `_fail` 对动作路径也执行识别专属的「恢复编辑器可编辑 + 同步控制器文本」——改为仅当确实在填充文本时执行。
- `_append_answer` 每个片段都 `setMarkdown` 整篇重解析（O(n²)），且流式中的半截代码块/表格会渲染错乱——改为流式期间追加纯文本，完成时一次性 `setMarkdown` 渲染。
- `perform(action)` 与规格约定的 `执行动作(动作, 文本)` 签名漂移（依赖 `set_text` 每次都被调用）——改为 `perform(action, text)`，由结果窗口显式传入编辑器当前文本。
- 动作进行中复制按钮被误启用——统一并入忙碌态。
- `ACTION_ORDER` 从结果窗口移入 `controller.py`，与 `Action` 同处定义，减少改动面。

**刻意的偏离（记录备查）**

- **与父规格冲突，需显式记录**：`spec.md` 在 `AppController` 的测试决策里写了「连续动作是追加而非覆盖」，而本票要求「答案随之更新」。实现选择**覆盖**（每次动作清空答案区）。「追加」应落在控制器的历史累积上，随 **08 历史记录**一并明确。
- `_answer.setOpenExternalLinks(True)`：答案里的链接可点——票面未要求，属小增。
- 动作按钮在流式进行中禁用，避免同一窗口并发请求。
